# IPO status and subscription repair — 2026-10-22

## What the supplied production payload showed

- 121 IPO records were returned.
- 10 records were labelled `Upcoming`; several had September close/listing dates.
- No record contained `subscriptionCategories`, so the category-wise detail table could not render.
- One duplicate NSE record had an implausible `₹88,642,911 Cr` issue size alongside a `₹0.17–₹0.18` band.
- The normalizer was stamping the Worker retrieval time into `updatedAt`, which could make an old provider record look newly updated.

## Code changes

- Lifecycle status is reconciled in the Worker cache response and again in the browser before the status filter runs. A passed tentative listing date is not treated as proof of a listing; without explicit `Listed` status or actual listing-price/gain evidence, the issue stays `Closed` pending confirmation.
- Obviously corrupted issue-size values expressed in crore are filtered. Historical rows with missing optional fields remain valid.
- Source `updatedAt` is preserved only when the provider actually supplies it; the Worker no longer stamps retrieval time as source freshness.
- The Xflot detail endpoint and `ipos.markets` subscription feed use the same subscription normalizer. It supports array/object category formats, offered shares, bid shares, subscription multiples, applications, source timestamps and exact/lower-bound semantics.
- Subscription issue matching supports normalized aliases and conservative name matching. The feed retries after a zero-match attempt, throttles after successful enrichment, and focuses detail requests on current/recent issues rather than the full historical catalogue.
- Daily subscription history is recorded only when reported values exist; missing figures are not estimated or converted to zero.

## Deploy steps

1. Keep the existing `MARKET_CACHE` namespace. Run `npx wrangler kv namespace list` to get its real ID and add it to the root `wrangler.jsonc` under `kv_namespaces` before a config-driven deployment. Do not use a placeholder ID.
2. Deploy the updated source (`npm run build`, then `npx wrangler deploy`, or use the connected Cloudflare build pipeline).
3. Ensure the production Worker has `MARKET_CACHE` bound to the same namespace and `REFRESH_SECRET` configured.
4. Trigger a one-time refresh: `curl -X POST https://bazaarbrief.in/admin/refresh -H "Authorization: Bearer YOUR_REFRESH_SECRET"`.
5. Check `/api/ipos`, `/api/ipos/refresh-status`, and Worker logs. The first subscription refresh may still show unavailable fields if the upstream provider is down or the issue cannot be matched; the UI should report missing data rather than fabricate it.

## Follow-up: category-wise subscription cards (2026-10-23)

- The subscription manifest can contain only a headline total and status. The Worker now fetches the full issue detail whenever category rows are absent, and falls back to the documented `?symbol=` lookup if the manifest detail path is unavailable or cannot be normalized.
- The normalizer accepts split NII fields (`sNII`/`SHNI`, `bNII`/`BHNI`) whether they appear as top-level values, category keys, or nested sub-categories.
- The IPO detail UI now always displays separate bNII, sNII and Retail cards, while retaining the detailed offered/bid/multiple table where the source provides it.
- The free `ipos.markets` API documents QIB, NII, RII, EMP, PH and SH category data; it documents NII as a combined category, not a guaranteed bNII/sNII split. Therefore bNII/sNII remain “Not disclosed” unless the selected provider explicitly supplies those values. The combined NII multiple is shown separately and is never copied into either split.
- Added tests for flat and nested split fields and for not fabricating split values from combined NII.


## Follow-up: application breakup and IST refresh cadence (2026-10-23)
- Added a dedicated Application-wise breakup table to IPO details, using provider-reported category application counts, offered/bid shares, and subscription multiples.
- Normalization now recognizes flat application-count fields for QIB, NII, bNII, sNII, Retail, Employees, and Shareholders, without fabricating missing counts.
- The existing every-15-minute Cloudflare cron is gated in the Worker using Asia/Kolkata time: all quarter-hour triggers from 09:00 to before 17:00 IST are used; outside that window, refreshes run only on the hour. The hourly schedule therefore starts at 17:00 IST and continues overnight.
- Cloudflare cron triggers are UTC-based; the runtime gate accounts for the IST half-hour offset.
